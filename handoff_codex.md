# FawterX Project Handoff - ETA Digital Signature Mismatch (Error 4043)

This document provides a comprehensive technical overview of the FawterX project, our achievements, the exact issue we are facing, and the necessary context to help Codex resolve it.

---

## 1. Project Overview & Architecture
FawterX is a web application designed to automate the integration with the **Egyptian Tax Authority (ETA) e-Invoicing Portal**. It allows users to upload Excel sheets of invoices, automatically maps them to the official ETA JSON schema, signs them digitally using a USB token (via a local C# bridge application), and submits them directly to the production/sandbox ETA APIs.

### Architecture:
* **Frontend:** React + Vite (SPA) hosted on Firebase Hosting ([fawterx.web.app](https://fawterx.web.app)).
* **Backend:** Node.js Express server running on port `5000` (used for token retrieval and database syncing).
* **Local Signer Bridge (`FawterX-Signer.exe`):** A lightweight C# console application running on port `8585` that communicates with the USB token (ePass2003, Egypt Trust, etc.) using standard Windows Cryptography APIs. It receives a pre-canonicalized string from the frontend, generates the CAdES-BES signature, and returns it.

---

## 2. What We Accomplished
1. **Fully Automated Pipeline:** Excel parsing, automatic column mapping, and direct API submission to ETA.
2. **CAdES-BES Digital Signing Bridge:** Developed a zero-dependency C# signer that successfully auto-selects certificates, prompts for the token PIN, and constructs the mandatory `ESS-Signing-Certificate-V2` attribute required by ITIDA / ETA.
3. **Recursive Object Cleaning (`cleanObject`):** Implemented a utility to recursively strip empty strings, empty arrays, and null/undefined values from both the submitted JSON and the string to be signed, ensuring optional fields don't cause hash mismatches.
4. **V2.6.0 Unicode Escaping (UTF-8 / ASCII):** Modified the JS canonicalizer to escape non-ASCII characters (such as Arabic descriptions) to `\uXXXX` (uppercase hex), matching C#'s native `StringEscapeHandling.EscapeNonAscii` serialization.

## 3. The Remaining Problem: Error `4043`
Despite these updates, the ETA portal returns the following rejection for documents signed via our pipeline:
```text
Step-03.ITIDA Signature Validator - Invalid Digital Signature
• 4043 4043:Exception[message-digest attribute value does not match calculated value]
```

### The Root Cause:
The `message-digest` error indicates that the **canonical string generated by our JavaScript `serializeToken` function in the frontend** differs (even by a single byte, casing, decimal zero, or ordering) from the **canonical string constructed internally by the ETA Portal's servers** when they recalculate the hash for validation.

---

## 4. Key Areas of Mismatch for Codex to Investigate

### A. Decimal / Float Precision Formatting
In JavaScript, floating-point numbers are formatted dynamically (e.g., `120.00` becomes `120`, `0.0` becomes `0`). 
The C# Newtonsoft.Json library (which ETA and standard signers use) preserves exact decimals when parsed as `decimal` type.
* **JS output:** `120` or `120.5`
* **ETA expected output:** Might expect `120.00` or a specific number of trailing zeros (like 5 decimals, e.g., `120.00000`).
* **Check:** Compare how `serializeToken` handles decimal properties versus ETA's expectations.

### B. Keys Sorting and Arrays
Our JS implementation sorts all keys case-insensitively using:
```javascript
const keys = Object.keys(object).sort((a, b) => {
  const upperA = a.toUpperCase();
  const upperB = b.toUpperCase();
  return upperA.localeCompare(upperB, 'en', { sensitivity: 'base' });
});
```
* Does ETA use case-sensitive or culture-invariant sorting?
* How are arrays of objects (like `invoiceLines`) sorted or serialized?
